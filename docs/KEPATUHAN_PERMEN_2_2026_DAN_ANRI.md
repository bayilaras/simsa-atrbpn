# Peta Kepatuhan SIMSA terhadap Permen ATR/BPN Nomor 2 Tahun 2026 dan Ketentuan ANRI

## 1. Tujuan dan batas dokumen

Dokumen ini memetakan kemampuan SIMSA terhadap pedoman pengelolaan arsip elektronik. PDF Permen ATR/BPN Nomor 2 Tahun 2026 diperlakukan sebagai **sumber normatif**, bukan sebagai instruksi untuk mengubah sistem. Permintaan pengembangan, prioritas fitur, dan keputusan implementasi tetap berasal dari pemilik aplikasi.

Peta ini adalah asesmen kesiapan perangkat lunak, **bukan opini hukum, audit resmi, sertifikasi keamanan, atau pernyataan kepatuhan penuh**. Status `Implemented` berarti kontrol sudah tampak pada kode di repositori; kontrol tersebut tetap harus diuji pada lingkungan produksi. Status `Partial` berarti fondasi tersedia tetapi ada gap kode, data, prosedur, atau infrastruktur. Status `Deployment required` berarti pemenuhan utamanya berada di luar kode atau belum tersedia.

## 2. Posisi SIMSA dalam ekosistem kearsipan pemerintah

SIMSA sebaiknya diposisikan sebagai **DMS/aplikasi substantif Ditjen Pengadaan Tanah dan Pengembangan Pertanahan (PTPP)** untuk mengelola dokumen kerja, dosir perkara/kegiatan, metadata teknis pertanahan, kendali berkas, dan layanan pencarian internal.

SIMSA **bukan pengganti SRIKANDI**. Peraturan ANRI tentang SRIKANDI menempatkan SRIKANDI sebagai aplikasi umum bidang kearsipan dinamis bagi instansi pusat dan pemerintah daerah. Rekod yang menjadi arsip dinamis resmi harus diregistrasi dan dikelola melalui SRIKANDI sesuai tata kelola instansi. SIMSA perlu diintegrasikan melalui API resmi, dengan pemetaan identitas, klasifikasi, metadata, status, dan bukti sinkronisasi yang dapat diaudit.

Rancangan batas sistem yang disarankan:

| Sistem | Tanggung jawab utama |
|---|---|
| SIMSA | Dosir dan dokumen substantif Ditjen PTPP, metadata teknis, alih media terkendali, pencarian, legal hold, serta persiapan retensi/penyusutan |
| SRIKANDI | Registrasi dan pengelolaan arsip dinamis resmi lintas instansi sesuai tata kelola ANRI |
| BSrE/PSrE | Sertifikat elektronik, tanda tangan/segel elektronik tersertifikasi, validasi sertifikat dan bukti waktu |
| Infrastruktur Kementerian | IAM, KMS, object storage, backup/DR, AV/DLP, SIEM, pemantauan, dan pengelolaan insiden |

## 4. Gap yang memblokir penggunaan produksi untuk arsip sensitif

SIMSA belum layak diklaim **siap untuk arsip Rahasia/Sangat Rahasia** sampai seluruh butir berikut ditutup dan diuji:

1. model clearance personal, need-to-know, tujuan akses, persetujuan berjangka, watermark identitas/waktu, dan pengendalian cetak;
2. object storage private yang tervalidasi, migrasi seluruh blob publik legacy, encryption-at-rest dengan KMS/HSM, versioning, serta mode immutable/WORM;
3. karantina upload, AV/content scanning, DLP, dan pencegahan file berstatus `not_scanned` tersedia untuk pengguna;
4. audit append-only/immutable, korelasi SIEM, alert real-time, sinkronisasi waktu, dan retensi audit;
5. integrasi tanda tangan/segel elektronik BSrE/PSrE; simulasi telah dibuat tidak sah dan penandatanganan gagal-tertutup, tetapi layanan tersertifikasi belum tersedia;
6. backup database **dan bitstream**, uji restore, disaster recovery, serta bukti RPO/RTO;
7. pentest independen, asesmen risiko, hardening, secret management, incident response, dan persetujuan pemilik risiko;
8. custom same-site domain untuk frontend/API beserta cookie, OAuth redirect, CORS, dan CSRF yang tervalidasi;
9. kredensial dan integrasi API SRIKANDI resmi; serta
10. validasi Unit Kearsipan Kementerian, ANRI, keamanan informasi, dan pejabat berwenang.

Sebelum gap tersebut ditutup, batasi pilot pada data sintetis atau arsip kelas Biasa/Terbuka yang telah disetujui pemilik data.

## 5. Backlog integrasi SRIKANDI minimum

1. Tetapkan sumber kebenaran untuk setiap metadata dan status; jangan membuat dua nomor registrasi resmi yang bersaing.
2. Dapatkan akses API resmi, sandbox, identitas organisasi/unit, klasifikasi, dan petunjuk teknis dari pengelola SRIKANDI.
3. Buat tabel pemetaan `simsa_record_id ↔ srikandi_record_id`, versi payload, status sinkronisasi, retry count, dan hash payload.
4. Gunakan idempotency key, outbox transaksional, retry dengan backoff, dead-letter queue, dan proses rekonsiliasi terjadwal.
5. Catat siapa, kapan, arah sinkronisasi, hasil, error, dan perubahan metadata tanpa menyalin rahasia ke log.
6. Tentukan aturan konflik, koreksi, pembatalan, pemindahan, penyusutan, serta legal hold lintas sistem.
7. Uji end-to-end bersama Unit Kearsipan dan pengelola SRIKANDI; simpan berita acara serta bukti uji.

## 7. Tata kelola pemeliharaan peta kepatuhan

Peta ini harus direviu setiap kali terjadi perubahan peraturan, JRA, kontrak API SRIKANDI, skema database, provider penyimpanan, model role, atau proses penyusutan. Setiap status hanya boleh dinaikkan setelah tersedia bukti uji, pemilik kontrol, tanggal uji, hasil, pengecualian, dan persetujuan pejabat yang berwenang.
